# 输入与输出数据合同

本合同定义新项目进入工具包前必须满足的数据结构。项目负责人和数据提供方应在建模前共同确认，不能到全线阶段才补问坐标、字段或照片对应关系。

## 1. 目录合同

生产项目建议结构：

```text
projects/<project-id>/
├─ project.json
├─ rules.json
├─ input/                   # 不进入 Git
│  ├─ pointcloud/
│  │  └─ site.laz
│  ├─ cameras.csv
│  ├─ panoramas/
│  └─ optional/
│     ├─ control_points.csv
│     └─ asset_ledger.csv
└─ workspace/               # 生成物，不进入 Git
```

项目配置和规则可以提交到私有仓库，但其中不得包含敏感绝对坐标或客户标识。需要保存真实配置时，应放在受控项目仓库或加密存储，而不是通用工具包。

## 2. 点云合同

### 2.1 当前核心支持

- 文件格式：`.las` 或 `.laz`；
- 必需维度：`X`、`Y`、`Z`；
- 推荐维度：`red`、`green`、`blue`、`intensity`、`gps_time`；
- 单位：米；
- 轴向：项目配置默认 Z-up；
- 数值：所有坐标必须有限，不接受 NaN/Inf。

其他格式应先用有记录的转换步骤生成 LAS/LAZ，保留原文件哈希、转换工具、版本和参数。

### 2.2 必须说明的元数据

| 字段 | 要求 |
|---|---|
| 来源类型 | LiDAR、摄影测量、Gaussian-derived points 或其他 |
| 获取时间 | 至少到日期或批次 |
| 单位 | 明确为米或提供换算 |
| CRS/EPSG | 已知则填写；未知必须为 `null`，不得猜测 |
| 垂直基准 | 已知则填写；未知必须为 `null` |
| LAS scale/offset | 由审计自动读取并保留 |
| 颜色位深 | 若有 RGB，说明 8 bit/16 bit |
| 强度含义 | 若有 intensity，说明设备或归一化方式 |
| 裁剪/滤波历史 | 说明是否已降采样、去噪、配准或坐标平移 |

由高斯场景导出的点，仅可称为“高斯派生点式观测”，除非文件确实包含且算法实际使用 covariance、scale、opacity、visibility 等原始高斯属性。

### 2.3 点云拒收条件

- 坐标单位未知；
- 坐标包含大量非有限值；
- 点数、包围盒与交付说明明显矛盾；
- 颜色或强度字段被错误解释；
- 多批数据坐标基准不同但没有转换记录；
- 数据已被未知方式重采样且无法追踪来源。

## 3. 相机轨迹 CSV 合同

编码使用 UTF-8 或 UTF-8 with BOM。必需列：

| 列 | 类型 | 说明 |
|---|---|---|
| `index` | integer | 唯一、严格递增的记录编号 |
| `timestamp` | number | 可排序的时间值，单位需在项目说明中记录 |
| `file` | string | 相对于 `panorama_root` 的路径或文件名 |
| `x`,`y`,`z` | number | 与点云相同坐标系和单位的相机位置 |

照片投影所需推荐列：

| 列 | 类型 | 说明 |
|---|---|---|
| `rot_x`,`rot_y`,`rot_z` | number | 相机姿态；必须记录角度单位、欧拉顺序和方向 |

CSV 不得出现重复 `index` 或重复 `file`。时间戳倒序、轨迹突跳或相邻位置零距离都必须进入审计报告并人工解释。

## 4. 全景影像合同

- 推荐格式：JPEG 或 PNG；
- 路径必须可由 CSV 的 `file` 解析；
- 影像投影类型、分辨率和视场模型应在项目说明中记录；
- 原图不得因前端展示而被覆盖；
- 若经过去畸变、拼接或缩放，派生图要使用新目录并记录参数；
- 对外样例必须移除 EXIF、位置、人物、车牌、站名和其他敏感标识；
- 通用 GitHub 仓库不得提交生产全景。

缺失照片不一定阻断纯几何流程，但会降低照片解释资产的证据等级；缺失比例和影响区间必须进入限制清单。

## 5. 可选真值合同

### 5.1 控制点

建议字段：

```csv
id,x,y,z,crs,vertical_datum,source,accuracy_m,note
```

必须区分用于配准的控制点和用于独立验证的检查点。参与拟合的点不能再次当作独立验证数据。

### 5.2 设备台账

建议字段：

```csv
external_id,type,subtype,chainage_m,side,status,source,note
```

台账证明资产“应存在”时，也不自动证明当前点云中可见；注册表仍要记录证据来源和观测状态。

### 5.3 人工标注

每条标注应含标注人角色、时间、参考数据、结论和不确定性。不得只保存截图而不保存结构化结论。

## 6. 项目配置合同

`project.json` 由 Schema 校验，关键字段包括：

- `project.id`：稳定项目标识；
- `project.confidentiality`：至少区分 internal/restricted/public-demo；
- `project.crs`：EPSG、垂直基准和控制点说明；
- `inputs`：相对于项目根目录的输入路径；
- `workspace`：所有运行输出路径；
- `segmentation`：分段长度、走廊宽度和高程缓冲；
- `reconstruction`：Pilot 长度、轨距和未观测立面策略；
- `quality`：拟合和 Mesh 门槛；
- `rules`：项目规则文件。

所有路径建议使用相对路径。不要提交用户目录、盘符路径、局域网共享路径或生产服务器地址。

## 7. 输出合同

### 7.1 运行清单

每个阶段必须生成 manifest，至少包含：

- `project_id`；
- 阶段名称和状态；
- 开始/结束时间；
- 工具包版本和 Git commit；
- 配置哈希；
- 输入与输出逻辑路径和哈希；
- 关键指标；
- 异常和限制。

### 7.2 分段清单

每段包含：稳定段 ID、起止里程、相机范围、空间包围盒、点数和输出文件。自动生成后必须人工检查。

### 7.3 资产注册表

资产注册表必须通过 Schema，详见 [资产注册表规范](ASSET_REGISTRY_CN.md)。

### 7.4 三维模型

正式 release 至少提供：

- clean 主模型；
- 对应资产注册表；
- 可选 candidate/evidence 模型；
- Mesh 审计结果；
- 格式、单位、轴向和局部原点说明；
- 文件 SHA-256；
- 已知限制。

不得只交付无法追踪来源的单个模型文件。

### 7.5 QA 报告

QA 报告应使用机器可读 JSON，并可附 PNG/HTML 人工审查页。`passed: true` 只代表报告中已实现的检查通过，不自动证明全部现场资产正确。

## 8. 精度字段合同

误差报告必须标明评价基准：

- `internal_fit`：相对当前点式证据；
- `control_check`：相对独立控制/检查点；
- `ledger_or_expert`：相对台账或专业人工判定。

建议几何指标：MAE、RMSE、P50、P90、P95、最大值、样本数和覆盖率。不要只报告均值。

缺少 CRS、垂直基准或独立真值时：

- `absolute_precision_ready` 必须为 `false`；
- 只能报告 `internal_fit`；
- 报告正文必须带限制说明。

## 9. 数据变更规则

- 原始输入只读；
- 派生数据写入 `workspace/derived/`；
- 不覆盖已冻结输入；
- 新批数据使用新 run 或 batch ID；
- 合并多批数据前记录转换和配准；
- 任何人工删除、补点、平移或旋转都必须进入 manifest；
- 生产数据清理按单位的数据保留制度执行，不由通用脚本自动删除。

## 10. 数据接收签字项

建模开始前，负责人应确认：

- [ ] 输入格式与字段满足合同；
- [ ] 坐标单位和轴向已确认；
- [ ] CRS/垂直基准为真实值或明确未知；
- [ ] 相机与点云使用同一坐标框架；
- [ ] 照片缺失和覆盖边界已统计；
- [ ] 数据保密等级和使用权限已确认；
- [ ] GitHub 仓库中不会出现生产输入；
- [ ] 已确定内部拟合与绝对精度的声明边界。
